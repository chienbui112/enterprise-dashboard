# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # Vite dev server with HMR
npm run build    # Type-check (tsc -b) then production build
npm run lint     # ESLint over the repo
npm run preview  # Serve the production build
npm run server   # Offline Sync backend (Express + ws, port 3001) — only needed for Offline Sync "Backend" mode
npm run dev:all  # Run Vite + the backend together (concurrently)
```

There is **no test runner** configured. `build` runs `tsc -b` first, so a type error fails the build. The `server/` folder is a standalone Node process (plain ESM JS, outside the `tsc`/Vite build) — it is **not** type-checked or bundled.

## Big Picture

This is a WebGIS performance demo (React 19 + TypeScript + MapLibre GL + Vite). [src/App.tsx](src/App.tsx) is a React Router setup (a landing page + one route per dashboard, registered from [src/config/dashboards.ts](src/config/dashboards.ts)) that swaps between **eight independent dashboards** (2D Fleet Tracking, 3D Buildings, Spatial Analysis, MotionStream Fleet, Offline Sync, Route Optimizer, Geofence Monitor, History Playback), each a `components/<X>/index.tsx` + `MapContainer*.tsx` (MapLibre) + `ControlPanel*.tsx` (UI). All except Offline Sync own a dedicated worker in `workers/`; **Offline Sync has no worker** — its "heavy lifting" is IndexedDB + a custom tile protocol on the main thread. **History Playback** is the inverse case: it owns a worker, but only for **one-shot** data generation — the worker has no `setInterval`/bbox, and the interactive playback + per-frame proximity detection run on the **main thread** (RAF loop). Add a dashboard = add one entry to [dashboards.ts](src/config/dashboards.ts) (route + landing card auto-register).

The central design principle is **the Web Worker owns the full dataset (100k drivers / buildings) and the main thread only ever sees the filtered viewport subset** (plus, in Spatial Analysis, a downcast copy of all 100k positions for off-viewport spatial queries). Understanding the optimizations below is essential before touching the data path — naive changes (rebuilding GeoJSON per tick, structured-clone across threads, rendering all points) reintroduce the exact GC/jank/GPU problems this project exists to avoid.

- **Struct-of-Arrays master state** ([src/utils/geoHelpers.ts](src/utils/geoHelpers.ts), [src/workers/dataParser.worker.ts](src/workers/dataParser.worker.ts)): driver state is flat typed arrays (`Float64Array` coords/bearing, `Uint8Array` status, separate `destLngs`/`destLats`), mutated **in place** every 5s tick — zero per-tick allocation.
- **Transferable zero-copy**: the worker packs results into `Float32Array`/`Uint8Array`/`Uint32Array` and transfers the `ArrayBuffer` ownership (not structured clone). Drivers are identified by `idx: number`, never strings; `driverId()`/`driverName()` derive strings only on demand (popup).
- **Object pool on main thread** ([src/components/MapContainer/index.tsx](src/components/MapContainer/index.tsx)): GeoJSON feature objects are built once, then mutated in place; only a new `slice` reference array is created so React/MapLibre detect the change.
- **Bbox viewport filter**: the worker returns only points inside the current viewport (expanded ~20% to prefetch). This is what makes "Network API Hits"/"Rendered" metrics change as you pan. The 3D worker is **stateful** too — it keeps the parsed buildings as a master array and re-filters by bbox on every `moveend`.
- **Interaction lock**: while panning/zooming the main thread sends `SET_INTERACTING`; the worker pauses filtering/sending and flushes on release.
- **Directed simulation**: drivers move **toward their destination** each tick (not random walk); `bearing` is computed as the azimuth to the destination, and a driver picks a fresh destination when it arrives. The static `destLngs`/`destLats` are sent to the main thread **once** via `INIT_DESTINATIONS` (transferable); ETA on click is computed client-side via haversine using `AVG_SPEED_KMH`.
- **Click selection follows live data**: clicking an arrow shows a popup with name/status/position/destination/distance/ETA + a dashed line to the destination. The selection is tracked by `selectedIdxRef`; on every data tick (or filter change), `refreshSelection` in [MapContainer.tsx](src/components/MapContainer/MapContainer.tsx) re-positions the popup, redraws the line, and recomputes ETA. If the selected driver leaves the visible set, the popup is closed.
- **Loading state**: [src/components/MapLoadingOverlay.tsx](src/components/MapLoadingOverlay.tsx) is a shared overlay with `pointerEvents:none`. Each dashboard wires its own signal — 2D uses `hasFirstData` (set on first `DATA_UPDATED`), 3D uses `isProcessing` (set true around `GENERATE_AND_PARSE`).
- **Per-tick kdbush index, rebuilt in the worker** ([src/workers/spatialAnalysis.worker.ts](src/workers/spatialAnalysis.worker.ts), [src/utils/spatialHelpers.ts](src/utils/spatialHelpers.ts)): the Spatial Analysis worker rebuilds a [`kdbush`](https://github.com/mourner/kdbush) over all 100k positions every 5s tick (positions mutated → tree stale). The underlying `ArrayBuffer` (`kd.data`) is transferred zero-copy; the main thread reconstructs the tree with `KDBush.from(buffer)` in O(1). Queries use [`geokdbush`](https://github.com/mourner/geokdbush) (`around()` for both radius and K-nearest) for haversine-correct results.
- **Dual-channel broadcast (Spatial only)**: the worker sends **two coordinate channels** per tick — (a) the viewport-filtered subset for rendering (`coords`/`bearing`/`status`/`idx`), and (b) the FULL `Float32Array` `fullLngs`/`fullLats` for all 100k. Reason: in Find Nearest mode, the K nearest matches may sit just outside the viewport when the user clicks near the edge — the kdbush is built over all 100k, so without full positions on the main thread we can't compute their distances. All 7 buffers are transferable in a single `postMessage`.
- **RAF interpolation between drip ticks (MotionStream)** ([src/components/MotionStream/MapContainerStream.tsx](src/components/MotionStream/MapContainerStream.tsx), [src/utils/interpolationHelper.ts](src/utils/interpolationHelper.ts)): the MotionStream worker pushes the viewport subset only **every 3s** (Grab/Uber-style "drip" to save bandwidth), but the main thread runs a `requestAnimationFrame` loop that **lerps each car between its last and next position** at 60fps so motion looks continuous. State is an idx-keyed `Map<number, Entry>` of pooled `Entry` objects (`lastLng/Lat`, `nextLng/Lat`, cached `bearing`, `seen` tick-stamp, reused GeoJSON `feature`); each 3s tick re-anchors `last` from the car's **current interpolated position** (NOT the previous target — that would jump backward), sets `next` to the new packet, and mark-and-sweeps cars that left the viewport into a free-list. Bearing is computed **once per tick** per car (constant along a straight lerp segment) and cached — never per frame. Cars newly entering the viewport snap (`last=next`) for one tick to avoid a wild lerp from a stale origin.
- **Per-frame setData cap (MotionStream)**: interpolation requires `setData` **every frame** (~16ms), which is the opposite of the 2D dashboard's once-per-5s `setData`. Rebuilding tens of thousands of rotating symbols per frame janks, so above `CAP_ENTER` (8000) visible cars the dashboard falls back to **snap** (setData once per 3s tick, no lerp) with hysteresis (`CAP_EXIT` 7000) to avoid flicker at the boundary; a notice shows on the panel. The RAF loop never stops — it also measures real FPS (frames counted, published ≤2Hz). The symbol layer MUST keep `icon-allow-overlap`/`icon-ignore-placement: true` (collision detection off) for the per-frame redraw to stay affordable; no clustering (smooth individual icons are the point).
- **Offline-first via IndexedDB (Offline Sync)** ([src/components/OfflineSync/](src/components/OfflineSync/), [src/utils/indexedDbHelper.ts](src/utils/indexedDbHelper.ts), [src/utils/tileCacheHelper.ts](src/utils/tileCacheHelper.ts), [src/utils/offlineSyncServer.ts](src/utils/offlineSyncServer.ts)): a local DB (`idb` lib) is the source of truth for user-drawn points/polygons + notes. Features are saved with `synced:false`; a `window` online/offline listener (plus a manual toggle that mirrors into `tileCacheHelper.netState.online`) triggers a **queue sync** that pushes each unsynced feature to a simulated in-memory server. **Conflict resolution is version-based**: each feature carries `baseVersion`; the server returns `conflict` if its version moved ahead of `baseVersion`, the feature is flagged `conflict:true` (excluded from the auto-queue) and the panel offers keep-local (rebase + re-push) or take-server.
- **Two sync modes behind a `SyncTransport` abstraction (Offline Sync)** ([src/utils/syncTransport.ts](src/utils/syncTransport.ts)): `index.tsx` only calls `transport.push/pull/notifyChange/onRemoteChange/simulateServerEdit`; the version/conflict/merge logic is identical for both modes. A panel toggle switches between:
  - **Local (`createLocalTransport`)** — multi-tab within one browser. `indexedDbHelper.ts` opens **two** IndexedDB DBs: a **per-tab local DB** `WebGIS_Local_<clientId>` (`offline-features` + `tile-cache`) and a **shared DB** `WebGIS_Shared` (`server-records` + `meta` seq). `clientId` is from `sessionStorage` (`getClientId()`) so **each tab is a distinct "machine"**; ids are `crypto.randomUUID()`. The "server" is `WebGIS_Shared` ([offlineSyncServer.ts](src/utils/offlineSyncServer.ts)): `pushToServer` is an **atomic version-check CAS inside one IndexedDB readwrite transaction** (serialized across tabs), bumping a global `seq`; tabs notify each other via `BroadcastChannel("offline-sync")`.
  - **Backend (`createRemoteTransport`)** — multi-browser/device via a small Node server in [server/](server/) (**Express + `ws`**, JSON-file persistence). `push`/`pull` are `fetch("/api/...")`, `onRemoteChange` is a WebSocket to `/ws` (server broadcasts `{type:"changed"}` after each write → client pulls). The WS **auto-reconnects with exponential backoff** and, on reconnect (not the first open), fires `changeCbs` to **pull missed changes immediately** (idempotent via the `seq` cursor). [vite.config.ts](vite.config.ts) proxies `/api` + `/ws` to `localhost:3001` (same-origin, no CORS). Run with `npm run server` (or `npm run dev:all`). If the backend is unreachable, the dashboard **auto-falls back to Local**. Verified working cross-browser (two different browsers in Backend mode sync in real time).
  - Shared mechanics (both modes): `triggerSync` is **pull-then-push**; `pullFromServer` is gated on `netState.online`; merge rule — unknown id → insert as synced replica; local pending edit + server moved ahead → flag conflict; local synced → adopt server. `seq`-based incremental pull (`lastSeqRef`); switching mode resets `lastSeqRef=0` and re-hydrates from the new server.
- **Offline map tile caching (Offline Sync)**: the map uses a **raster** style whose tiles route through a custom `offline://` protocol ([tileCacheHelper.ts](src/utils/tileCacheHelper.ts) `registerOfflineTileProtocol`). The handler serves tiles from the IndexedDB `tile-cache` store first; when online it fetches + caches (cache-on-browse); when offline-and-uncached it returns a gray fallback tile. A "Tải vùng này" button additionally prefetches the whole viewport (current zoom + 1) via slippy-tile math. Vector tiles can't be cached this way — the raster style is a requirement, not a style choice.
- **TSP on a precomputed matrix, solved in a stateless worker (Route Optimizer)** ([src/workers/tspSolver.worker.ts](src/workers/tspSolver.worker.ts), [src/utils/osrmHelper.ts](src/utils/osrmHelper.ts), [src/utils/routeApiHelper.ts](src/utils/routeApiHelper.ts)): unlike the other workers, this one holds **no state and does no fetching** — the main thread fetches an OSRM `/table` **road** distance/duration matrix (fallback: haversine matrix) and hands it down; the worker is a **pure matrix solver** that never sees coordinates. It runs Nearest Neighbor → 2-opt → **Held-Karp** (exact DP, only when `N ≤ EXACT_MAX=20`: the `dp[mask][j]` table is a `(1<<n)*n` `Float32Array` ~84MB, ~1–2s, off the UI thread; above that it's skipped and the 2-opt tour is returned). Detailed road geometry comes from a single OSRM `/route` call (`steps=true`, split per-leg by concatenating step geometries; fallback: synthetic sine-bent polyline in `routeApiHelper.ts`). Geometry/matrices/NN-overlay coords live in **refs**; only the ordered result + totals reach React state. Both OSRM calls go straight from the browser (no backend) and **fall back gracefully** (panel reports the source), mirroring the project's auto-fallback ethos.
- **Multi-modal route + NN overlay rendering (Route Optimizer)** ([src/components/RouteOptimizer/MapContainerTsp.tsx](src/components/RouteOptimizer/MapContainerTsp.tsx)): the route source is a `FeatureCollection` of per-leg `LineString`s tagged with a `mode`, drawn by **two** line layers (`route-ride` solid green / `route-walk` dashed blue) filtered on `mode` — because `line-dasharray` is **not** data-driven in MapLibre (you can't vary the dash per-feature via a `["get",...]` expression). The mode split is **illustrative** (OSRM demo is car-only). An optional `compare-line` layer overlays the raw NN tour as **straight** dashed-red segments to expose the crossing edges that 2-opt/Held-Karp untie. Drawing is driven by imperative callbacks (`renderPointsRef`/`drawRouteRef`/`clearRouteRef`/`drawCompareRef`, same pattern as MotionStream's `packetHandlerRef`) so geometry stays out of React state.
- **Spatial-grid two-phase geofencing, stateful worker (Geofence Monitor)** ([src/workers/geofence.worker.ts](src/workers/geofence.worker.ts), [src/utils/geofenceHelpers.ts](src/utils/geofenceHelpers.ts)): the worker owns **50k vehicles** (SoA, clustered around 12 Vietnam city anchors — each vehicle roams within `ROAM_RADIUS` of a "home" so fleets stay on land and keep crossing zones) + **1000 arbitrary polygons** and ticks every **250ms**. Per tick it runs a **3-layer point-in-polygon pipeline** for *all* vehicles (not just the viewport): (0) a **uniform spatial grid** (`buildSpatialGrid`, ~0.3° cells over the country bbox) hashes each polygon into every cell its bbox touches; a vehicle maps to one cell and only tests the polygons registered there — this is what makes the larger area tractable (turns `O(vehicles × allZones)` into `O(vehicles × zonesPerCell)`); (1) **bbox** algebra (`zoneBboxFlat`, still needed because a polygon's bbox can spill into a neighbour cell); (2) **Turf `booleanPointInPolygon`** on the survivors (coord array passed directly — no per-call allocation). The worker counts real PiP calls (`pipCount`) so the panel can show grid efficiency vs. the `50k×1000` brute-force figure. **State cache = `Int16Array zoneOf`** (current zone id per vehicle, `-1` = outside) — a transition fires an Enter/Exit alert **only** when `zoneOf` changes (`primed` makes tick 0 a silent baseline so vehicles spawned inside a zone don't all alert). Render channel is the usual viewport-filtered two-pass count-then-pack + a `Uint8Array violating` flag; vehicles draw as a **GPU `circle` layer** with data-driven color (red = violating). A `SET_SPEED { factor }` message scales `BASE_STEP`/jitter live (0 = frozen, no new events).
- **Space-time cube + RAF playback + proximity hash grid (History Playback)** ([src/utils/playbackHelpers.ts](src/utils/playbackHelpers.ts), [src/workers/playbackHistory.worker.ts](src/workers/playbackHistory.worker.ts), [src/components/HistoryPlayback/MapContainerPlayback.tsx](src/components/HistoryPlayback/MapContainerPlayback.tsx)): replays **5000 vehicles over 300s**. The whole history is **one flat `Float32Array` "cube"** laid out `[frame][vehicle][lng,lat]` (`offset(t,i)=t*stride+i*2`, `stride=count*2`) — the vehicle id **is** its index `i` (stable across frames, never stored), and the required `Map<timestamp, frame>` ([`buildFrameIndex`](src/utils/playbackHelpers.ts)) holds **zero-copy `subarray` views** onto that buffer → O(1) seek, ~12MB total. The worker generates the cube **once** and transfers it (no `setInterval`). The main thread runs a **`requestAnimationFrame` loop** that advances `time += dt × speed` and **lerps each vehicle between adjacent integer-second frames** (60fps regardless of 1×–60× speed), then runs **proximity detection every frame on the interpolated positions** via [`ProximityDetector`](src/utils/playbackHelpers.ts) — a **uniform hash grid whose cell = the 5m threshold**, so each vehicle is tested only against the 9 surrounding cells (`j>i`), collapsing the `~12.5M`-pair O(N²) sweep to ~O(N). Bucket arrays + `cellIdx` are reused (near-zero alloc/frame). A near-collision is logged only on the **onset** transition (pair newly < 5m, like geofence's Enter cache); each hit draws an amber-halo+red-core warning circle. The slider is two-way via a **`seekNonce` token** (RAF publishes time back throttled ~16Hz; manual scrub bumps the nonce → re-seek without a feedback loop). A **ruler tool** (`measureMode`) pauses playback and turns clicks into A→B vehicle selection, drawing a dashed line + haversine distance label that also tracks on scrub; selection lives in refs (`measureARef`/`measureBRef`), nothing per-frame hits React state while playing.
- **Custom WebGL shader + Instanced Rendering flood digital twin (3D Flood Twin)** ([src/utils/floodHelpers.ts](src/utils/floodHelpers.ts), [src/utils/floodLayers.ts](src/utils/floodLayers.ts), [src/workers/floodSim.worker.ts](src/workers/floodSim.worker.ts), [src/components/FloodSim/](src/components/FloodSim/)): the **only** dashboard that drops below the MapLibre style abstraction into raw GLSL via **two `CustomLayerInterface` layers** sharing the map's GL context. (1) `FloodWaterLayer` is a **large flat quad** (~55 km, `SCENE_HALF_DEG_WATER`, low-res grid) held **perfectly flat** at `u_levelZ` — the wave look is done **entirely in the Fragment Shader**, NOT by displacing vertices (rippled geometry intersects walls at an uneven, jittering waterline). Two things keep it smooth & zoom-stable: (a) waves are computed from **real-world metres** (`v_local = (a_pos − u_origin) / u_meter`) so the wavelength is fixed in world space regardless of zoom/plane size (NOT from a 0..1 uv, which stretched per zoom); (b) the plane is far larger than the viewport so its square edge is never visible when zooming out. The synthetic buildings render at **`fill-extrusion-opacity: 1.0`** (fully opaque → clean depth) so the translucent water blends over them without order ambiguity. It draws with `gl.POLYGON_OFFSET_FILL` using **constant bias only** (`polygonOffset(0, −4)`) — the slope **factor must stay 0**, because a near-horizontal plane viewed obliquely has a huge depth slope, so any non-zero factor makes the water "win" the depth test wrongly and climb over walls at oblique pitch (top-down looks fine since the slope is ~0 there). The constant −4 bias makes the water reliably win the **far-field z-fight against the ground/terrain** (two near-parallel near-coplanar surfaces) so a uniform flood covers the whole low ground consistently instead of flickering in patches; vertical walls are far from coplanar so the bias barely shifts the building waterline. The plane is a **single quad** (`segments: 1`) — a dense grid made the z-fight show as a cellular pattern along its tessellation. `maxPitch` is capped at 70 to avoid grazing the horizon (worst-case depth precision). It's **translucent** (`depthMask(false)`, alpha blend, drawn **last**) so it reads the building/props depth and submerges anything shorter than the water level. It calls `map.triggerRepaint()` every frame → continuous 60fps wave animation. (2) `InstancedPropsLayer` draws thousands of trees (trunk box + 2 stacked cones) and rescue barriers (box + reflective stripe) via **`drawArraysInstanced`** (WebGL2) / `ANGLE_instanced_arrays` (WebGL1 fallback): one shared base-mesh VBO + a small per-instance VBO (`[mercX, mercY, scale, rot]`), so VRAM stays flat regardless of count; its Fragment Shader tints any vertex below `u_waterMeters` blue (parts "underwater"). All geometry is authored in **local metres** and scaled by `u_meter` (`MercatorCoordinate.meterInMercatorCoordinateUnits()` at scene centre) since custom-layer z is conformal. The slider spans **0–5 m**; against tall towers that reads as a thin sheet, so the water-plane z **and** the props' underwater-tint threshold are both multiplied by `FLOOD_VIS_SCALE` (×4, vertical exaggeration — slider still reads real metres); scaling both keeps the submersion line consistent. Water is bright **cyan/blue**, submerged prop geometry is tinted blue to match, and the layer **skips drawing entirely when level ≈ 0** (the wave displacement around z=0 would otherwise clip object bases) while still calling `triggerRepaint()` so raising the slider re-shows it immediately. Buildings/trees/barriers/water use four distinct hues (light-gray / green / orange / blue) so they read apart on the dark basemap. (Mercator only; no globe — see the matrix note below.) **The slider bypasses React entirely**: water level lives in a `useRef<{meters}>` shared object handed to both layers at construction; the uncontrolled `<input type=range>`'s `onChange` mutates `waterRef.current.meters` (the sanctioned ref escape hatch — never replace the object, the layers hold its identity) and updates the thumb + numeric `<span>` via DOM refs, so dragging never triggers a component re-render — the GPU just reads the new uniform next frame. A "storm" `setInterval` ramps the same path 0→5m. Layers are added **after** the `fill-extrusion` buildings layer for correct depth ordering; `onRemove` deletes all buffers/programs. **Gotcha:** MapLibre leaves `gl.CULL_FACE` *enabled* from its own layers, so both custom layers must `gl.disable(gl.CULL_FACE)` in `render()` — otherwise the horizontal water plane (and self-generated cone/box faces with arbitrary winding) get back-face-culled and never appear. The render matrix MUST be `args.defaultProjectionData.mainMatrix` — this is the mercator `[0..1]`→clip matrix that `MercatorCoordinate` vertices need, per the official v5 custom-layer example. Do **not** use `args.modelViewProjectionMatrix`: it transforms the geometry off-screen and nothing renders (silent failure — native layers still draw, so only the custom layers vanish), which is the trap this dashboard hit first. **IoT water-level feed:** the panel has a `📡 Cảm biến IoT / ✋ Thủ công` toggle. In IoT mode it opens a WebSocket sensor feed ([src/utils/floodSensorFeed.ts](src/utils/floodSensorFeed.ts) → `/ws-sensors`, served by [server/sensorFeed.js](server/sensorFeed.js)) whose readings call the **same** `setLevel` (so the slider thumb + label + uniform stay in sync); the slider/storm are disabled. The feed reconnects with backoff (pattern copied from `createRemoteTransport`) and **falls back to a client-side simulator** when the backend is unreachable (so `npm run dev` still works), reporting `live`/`simulated`/`connecting` via a status chip. **Critical:** the sensor feed uses a SEPARATE `/ws-sensors` path + its own `WebSocketServer` so it never collides with Offline Sync's `/ws` (whose client treats any message as "changed"). **Scene-source toggle (`🏙️ Synthetic` / `🗼 MapTiler` / `🌍 Google`):** Synthetic = generated buildings/props. **MapTiler** = real 3D buildings from MapTiler OpenMapTiles **vector** tiles via native MapLibre `fill-extrusion` on the `building` source-layer (`render_height`/`render_min_height`) — NOT deck.gl/3D-Tiles (the MapTiler `v3-openmaptiles/tiles.json` is a vector tileset, not OGC 3D Tiles). **Google** = Photorealistic OGC **3D Tiles** via deck.gl `Tile3DLayer` + `MapboxOverlay({interleaved:true})` ([src/utils/google3dTiles.ts](src/utils/google3dTiles.ts)) sharing the depth buffer, deck layer inserted `beforeId` the water layer. Both real-world sources hide the synthetic buildings/props. **DEM terrain** (`raster-dem` Terrarium tiles + `map.setTerrain`, no key) applies to Synthetic **and** MapTiler (Google supplies its own terrain). MapTiler keys are **origin-restricted** — a 403 "Key usage restricted" means the origin isn't allowlisted at cloud.maptiler.com; override via `VITE_MAPTILER_KEY`. deck.gl + loaders.gl are isolated in a lazy `deckgl` vendor chunk (~270KB gzip). A **basemap switcher** (`🌑 Tối / ☀️ Sáng / 🗺️ Voyager`, Carto styles) calls `map.setStyle()` — which wipes all sources/layers/terrain/overlay — so the rebuild is centralized in a `setupAfterStyle()` run on the initial `load` AND on `map.once("styledata")` after each switch (re-adds buildings source/layer, resets `addedRef`/`propsLayerRef` so the custom layers re-instantiate, then re-runs scene/tiles/terrain sync); the deck overlay is removed before `setStyle` and re-added by the tiles sync. **The Google key needs the "Map Tiles API" enabled on its Cloud project** or the tileset 403s (`SERVICE_DISABLED`) — the dashboard shows an error chip and stays on synthetic; override the key via `VITE_GOOGLE_3D_TILES_KEY`. A full analysis (3D Tiles/HLOD, DEM, instancing at scale) lives in [docs/flood-architecture.md](docs/flood-architecture.md). **Panel readouts** ([ControlPanelFlood.tsx](src/components/FloodSim/ControlPanelFlood.tsx)): *Nguồn cảnh 3D* picks the city source (synthetic / MapTiler / Google); *Địa hình DEM thật* + *Phóng đại* toggle/scale the terrain (synthetic & MapTiler only); the *3D Tiles* chip is the Google load state (idle/loading/ready/error); *Bản đồ nền* switches the Carto base; *Nguồn mực nước* = IoT-feed vs Manual with a LIVE/SIMULATED/CONNECTING chip; *Mức độ ngập lụt X.X m* is the real-metre water level driving the uniform (rendered ×`FLOOD_VIS_SCALE`); the scene metrics are generated counts — *Toà nhà* = building features, *Cây xanh*/*Rào chắn* = instance counts, *Worker sinh cảnh* = one-shot generation time (ms), *Tổng vật thể props* = trees+barriers (the single-upload instancing figure). Mirrored in README §15.6.
- **Leak safety**: `MapContainer*` removes listeners + closes the popup + calls `map.remove()`; the dashboard `index.tsx` calls `worker.terminate()` on unmount. Switching modes via the menu unmounts the other dashboard, so cleanup must stay correct.

### Main ↔ Worker message contracts

2D (`dataParser.worker.ts`): main→worker `INIT_DATA`, `UPDATE_BBOX`, `TOGGLE_FILTER`, `SET_STREAMING`, `SET_INTERACTING`; worker→main `INIT_DESTINATIONS` (static dest coords, sent once), `DATA_UPDATED` (`{ count, coords, bearing, status, idx }`, transferable).

3D (`dataParser3d.worker.ts`): main→worker `GENERATE_AND_PARSE { count }`, `UPDATE_BBOX { bbox }`; worker→main `GENERATE_DONE { total, parseMs }`, `VISIBLE_DATA { payload }`. The worker generates a large JSON string and `JSON.parse`s it inside the worker to keep the parse cost off the main thread.

Spatial (`spatialAnalysis.worker.ts`): main→worker `INIT_DATA { count, bbox }`, `UPDATE_BBOX { bbox }`, `SET_STREAMING { isActive }`, `SET_INTERACTING { isActive }`; worker→main `INIT_DESTINATIONS { destCoords }` (sent once), `DATA_UPDATED { count, coords, bearing, status, idx, fullLngs, fullLats, kdData }` (all 7 buffers transferable). Note: no `TOGGLE_FILTER` — bbox filter is always on for the rendering channel; the full-positions channel is unconditional.

MotionStream (`motionStream.worker.ts`): main→worker `INIT_DATA { count, bbox }`, `UPDATE_BBOX { bbox }`, `SET_STREAMING { isActive }`, `SET_INTERACTING { isActive }`; worker→main `DATA_UPDATED { count, coords, bearing, idx }` (transferable). Tick cadence is **3000ms** (`STREAM_INTERVAL`, must match the main-thread lerp window). Streaming starts inside `INIT_DATA` (a static fleet is a bad demo). No `INIT_DESTINATIONS`/`TOGGLE_FILTER`; `idx` is mandatory (it's the interpolation key); no `status` (cars aren't colored by status here). The dashboard hands packets to the map via a `packetHandlerRef` callback rather than React state, so the 0.33Hz worker stream never re-renders the dashboard tree.

Route Optimizer / TSP (`tspSolver.worker.ts`): main→worker `SOLVE_TSP { matrix: number[][], n, startIndex }` (cost matrix in **metres** — OSRM road distances or haversine fallback); worker→main `SOLVED { order, nnOrder, nnCost, twoOptCost, exactCost|null, optimal }`. Unlike the other workers this one is **stateless and self-contained per call** — it does no `setInterval`, no bbox, no fetching; OSRM `/table`+`/route` and the synthetic fallback all live on the main thread ([osrmHelper.ts](src/utils/osrmHelper.ts), [routeApiHelper.ts](src/utils/routeApiHelper.ts)). `exactCost` is `null` when `N > 20` (Held-Karp skipped).

Geofence Monitor (`geofence.worker.ts`): main→worker `INIT_DATA { count, geofenceCount, bbox }`, `UPDATE_BBOX { bbox }`, `SET_STREAMING { isActive }`, `SET_INTERACTING { isActive }`, `SET_SPEED { factor }` (movement-speed multiplier, 0 = frozen); worker→main `GEOFENCES_READY { geojson }` (polygon FeatureCollection, sent **once** for drawing), `DATA_UPDATED { count, coords, violating, idx, totalViolating, pipCount, alerts }` (`coords`/`violating`/`idx` transferable; `alerts` is a small `{ idx, zone, type:"enter"|"exit" }[]` of transitions only), and `ALERTS_ONLY { alerts, totalViolating, pipCount }` (sent **during** pan/zoom so monitoring never pauses, without re-packing the render frame). Detection runs over all vehicles regardless of viewport; only the render channel is bbox-filtered.

History Playback (`playbackHistory.worker.ts`): main→worker `GENERATE { count, frames }`; worker→main `GENERATED { cube, count, frames, stride, genMs }` (the `cube` `ArrayBuffer` is **transferable**). This worker is **stateless and one-shot** — it generates the space-time cube once and exits the message loop; there is no streaming/bbox/interaction message because playback + proximity detection live entirely on the main thread (RAF loop in `MapContainerPlayback.tsx`).

3D Flood Twin IoT sensor channel (NOT a worker — a WebSocket): server→client on path **`/ws-sensors`** (its own `WebSocketServer` in [server/sensorFeed.js](server/sensorFeed.js), separate from Offline Sync's `/ws`), `{ type:"sensor", stationId, level, ts }` every ~500ms (`level` 0–5 m, tide+surge curve). The client ([floodSensorFeed.ts](src/utils/floodSensorFeed.ts)) ignores non-`sensor` frames, reconnects with backoff, and auto-substitutes a client-side simulator when the backend is down. No client→server messages. Vite proxies `/ws-sensors` (ws) alongside `/ws` and `/api`.

3D Flood Twin (`floodSim.worker.ts`): main→worker `GENERATE { buildingCount, treeCount, barrierCount }`; worker→main `SCENE_READY { buildings, trees, barriers, treeCount, barrierCount, genMs }`. **Stateless and one-shot** (like History Playback): the worker builds a clustered city — `buildings` is a parsed GeoJSON `FeatureCollection` with `height`/`min_height`/`base_color` (heavy JSON string built + `JSON.parse`d in-worker, sent as a structured-clone object since count is only a few thousand), while `trees`/`barriers` are flat `Float32Array`s (`[lng, lat, scale, rot]` per instance, `TREE_STRIDE`/`BARRIER_STRIDE = 4`) **transferred zero-copy**. There is no streaming/bbox/interaction message — flood playback + wave animation run entirely on the main thread in the two custom WebGL layers.

When adding a message type, update both the worker's handler and the `index.tsx` orchestrator — the contract is hand-maintained on both sides.

## Non-obvious patterns & gotchas

- **Ref-for-prop closure pattern**: map listeners are registered once in `useEffect(..., [])`, so any prop they read (e.g. `onMapMove`, `destinations`) is captured at first render and goes stale. The fix used throughout is to mirror the prop into a ref updated each render (`onMapMoveRef.current = onMapMove`) and have the listener read `onMapMoveRef.current`. The same pattern wraps `isInteracting` and the active selection. Reach for this any time you add a new listener that needs the latest prop/state.
- **Two-pass count-then-pack in `processAndSend()`** ([dataParser.worker.ts:90-113](src/workers/dataParser.worker.ts#L90-L113)): the 2D worker walks the 100k drivers **twice** per tick — pass 1 counts how many pass the bbox filter, pass 2 allocates `Float32Array`/`Uint8Array`/`Uint32Array` at the exact size and packs into them. This is deliberately not `array.push()` + later conversion: dynamic arrays would realloc multiple times and then need a final copy into typed arrays (defeating the transferable). Two tight loops over typed arrays are cheaper than one loop that grows a dynamic buffer. Preserve this shape when adding new per-driver output channels.
- **`setData` per tick is intentional, not a missed optimization**: every point moves every tick in the simulation, so `source.updateData()` (diff) provides no benefit. Don't switch to it without first changing the simulation to per-driver deltas.
- **Popup uses `closeOnClick: false`** ([MapContainer.tsx](src/components/MapContainer/MapContainer.tsx)) on purpose: with the default, the same click that opens the popup also triggers its close handler, which clears the selection line ("line flashes then disappears"). Closing happens only via the X button — and `popupRef.current?.remove()` must run **before** the new selection's `setData`, otherwise the old close handler wipes the line you just set.
- **Don't reinstall `@types/maplibre-gl`**: maplibre-gl v5 ships its own types. The DT package is v1 and conflicts with v5 type definitions.
- **Worker `self.postMessage` typing**: tsconfig uses `lib: ["DOM"]` (not WebWorker), so `self` is inferred as `Window` and the transferable overload disappears. Both workers cast via a local `const post = self.postMessage as (message: unknown, transfer?: Transferable[]) => void`. Reuse that pattern for new workers.
- **3D `fill-extrusion` only stays tractable at 100k thanks to viewport filtering** — if you remove the bbox filter or extend the dataset, expect GPU jank at low zoom where most of the dataset is in view.
- **Hand-rolled buffer circle, not Turf** ([src/utils/spatialHelpers.ts](src/utils/spatialHelpers.ts)): `createBufferCircle` generates a 64-step polygon using an equirectangular approximation (`dLat = R/111`, `dLng = R/(111·cos(lat))`). At radii of a few km the error vs. a true geodesic circle is sub-meter — far cheaper than pulling in Turf for *this* case. **`@turf/turf` IS now imported — but only in [geofence.worker.ts](src/workers/geofence.worker.ts)** for `booleanPointInPolygon` (arbitrary polygons, where the hand-rolled approach doesn't apply). It tree-shakes to ~few KB in that worker chunk; don't add it to the Spatial Analysis path (the buffer circle stays hand-rolled). The ControlPanelSpatial footer text claiming Turf is unused is stale.
- **kdbush rebuilt every tick, on purpose**: do not try to update the tree incrementally — every driver moves every tick, so an "update" is equivalent to a full rebuild anyway, and the build cost (~30–50ms for 100k) is in the worker where it doesn't block UI. The transfer of `kd.data` as a single `ArrayBuffer` is what makes this affordable across the thread boundary.
- **Offline tile protocol is global + registered before the map mounts**: `maplibre.addProtocol("offline", …)` is a static/global registration, so the Offline Sync dashboard registers it in its setup (after opening IndexedDB, before rendering the map — the map is gated on a `ready` state) and `removeProtocol` on unmount. The prefetch URL builder and the raster source's tile template MUST resolve to the **same** concrete URL (a single fixed subdomain `a.basemaps.cartocdn.com`, no `{s}`) or prefetched tiles won't be cache hits at runtime. The protocol reads `netState.online` (mirrored from the React online state) — gating on the simulated flag, not `navigator.onLine`, is what makes the "Go Offline" toggle actually block tile fetches in the demo.
- **`line-dasharray` is not data-driven (Route Optimizer)**: to render `walk`=dashed + `ride`=solid you MUST split into two `line` layers filtered by a `mode` property — you cannot vary the dash per-feature via a `["get",...]` expression (`line-color` can be data-driven; the dash pattern cannot). Same for the straight dashed-red NN overlay — it's its own `compare-line` layer.
- **Held-Karp is capped at `N ≤ 20` for a reason**: the DP table is `(1<<n)*n` (`Float32Array`, ~84MB at n=20) and the inner loop is O(N²·2ⁿ) (~1–2s at n=20). Above 20 it's intentionally skipped (2-opt result returned). Don't raise `POINT_COUNT` past 20 expecting exact solutions — and don't reach for a Genetic Algorithm at this scale: Held-Karp already returns the provably optimal tour, GA only earns its keep at larger N or with VRP-style constraints.
- **OSRM calls fail open, not closed (Route Optimizer)**: `fetchOsrmTable`/`fetchOsrmRoute` throw on any non-`Ok`/network error; the orchestrator catches and substitutes a haversine matrix + synthetic per-leg polyline, flipping `sourceRef` to `"fallback"`. The public demo server (`router.project-osrm.org`) is rate-limited — treat a fallback as expected, not a bug. Don't add a hard dependency on OSRM being reachable.

## Conventions

- **Code comments are written in Vietnamese.** Match the surrounding language when editing existing files.
- **React Compiler is enabled** (`babel-plugin-react-compiler` via [vite.config.ts](vite.config.ts)). Manual `useMemo`/`useCallback`/`memo` are generally unnecessary; do not add them reflexively. Follow the Rules of React so the compiler can optimize.
- Coordinates default to the Hanoi area (`lng 105.75–105.93`, `lat 20.95–21.10`); ETA uses `AVG_SPEED_KMH = 25` with haversine distance (great-circle, not real routing) — **except Route Optimizer**, which uses real OSRM road distance/duration (falling back to haversine only when OSRM is unreachable).
- `maplibre-gl` is split into its own `maplibre` vendor chunk in [vite.config.ts](vite.config.ts) — keep heavy vendor deps out of the app chunk.
